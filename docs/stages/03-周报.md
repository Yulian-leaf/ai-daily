## 1. 需求与范围

- **周报节奏**：每周两次（周一 + 周四）。
- **周报内容**：汇总最近一段时间的已上墙日报条目，由 LLM 生成结构化综述（标题 / 综述正文 / 按子领域分组的亮点 / 趋势 / 展望）。
- **日报/周报切换**：前端顶部导航，两个独立页面互跳。
- **衔接 Phase 3.5**：双周报告（聚合 14 天、偏趋势对比）+ 海报化设计——本阶段先把「weekly」基本盘做通，3.5 在其上增量扩展，避免返工。

## 2. 数据模型：`weekly_reports` 表

在 SQLite 中新增一张表（沿用 items / summaries 的建表与迁移套路）：

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `id` | INTEGER 主键自增 | 报告编号 |
| `period` | TEXT 默认 `weekly` | 周期类型：`weekly` / `biweekly`（为 3.5 预留） |
| `week_start` | TEXT | 报告覆盖起始日 `YYYY-MM-DD` |
| `week_end` | TEXT | 报告覆盖结束日 |
| `title` | TEXT | 周报标题（LLM 生成） |
| `overview` | TEXT | 综述正文（LLM 生成） |
| `highlights_json` | TEXT | 亮点列表 JSON：`[{field, title, url, summary}]` |
| `trend` | TEXT | 跨周趋势洞察（LLM 生成） |
| `outlook` | TEXT | 下周展望（LLM 生成） |
| `generated_at` | TEXT | 生成时间 |

**幂等约束**：`UNIQUE(period, week_start)`——同一周期重复生成，覆盖更新而非新增，天然防止重复周报（呼应「每日封顶」的幂等思想）。

## 3. 生成流程：`src/weekly.py`

新增 `run_weekly_cmd(period)`，流水线如下：

```
① 计算窗口：weekly = 最近 7 天，biweekly = 最近 14 天（week_start = 今天 - N 天）
② 取输入：storage.get_surfaced_since(week_start) → 窗口内已上墙的日报条目
            （每条只取 title + field + 一句话摘要 innovation + score + url）
③ 判空：窗口内条目 < 阈值（默认 3 条）→ 跳过生成，避免产出空周报
④ 生成：prompts/weekly.txt 喂给 LLM → 结构化 JSON（title/overview/highlights/trend/outlook）
⑤ 入库：storage.save_weekly_report(...)（按 period+week_start upsert）
⑥ 渲染：web.render_weekly(...) → weekly.html（本期 + 历史归档）
```

**关键设计决策**：

1. **周报的输入 = 已上墙日报条目**，不重新抓取、不重新打分/总结。周报是「top 中的 top」——日报已经完成了筛选与单条总结，周报只做汇总综述。这样成本极低（每次只 1 次 LLM 调用）。
2. **highlights 的 url 必须照抄输入**：提示词里明确要求「url 必须原样复制输入列表里的值」，防止 LLM 幻觉出不存在或错误的链接。
3. **窗口滚动式而非日历式**：`week_start = 今天 - 7 天`，避免处理「周一/周四」的日历边界，简单可靠；如需严格对齐周一/周四，后续再加日历计算。

## 4. 提示词：`prompts/weekly.txt`

AI4S 周报科研编辑人设，输入是「过去 N 天的日报条目清单」，输出严格 JSON：

```json
{
  "title": "AI4S 周报 · MM-DD ~ MM-DD",
  "overview": "3-5 句综述，讲清本周 AI4S 的主旋律",
  "highlights": [
    {"field": "protein", "title": "...", "url": "...", "summary": "一句话亮点"}
  ],
  "trend": "跨周趋势 / 变化",
  "outlook": "下周展望"
}
```

要求：中文、量化优先、按 8 个子领域分组、url 照抄输入、只输出 JSON。

## 5. 存储方法：`src/storage.py`

- 建表：在 `_SCHEMA` 里加 `weekly_reports` 的 `CREATE TABLE IF NOT EXISTS`（沿用现有建表 + 幂等迁移思路）。
- `save_weekly_report(report)`：`INSERT ... ON CONFLICT(period, week_start) DO UPDATE`（upsert）。
- `get_weekly_reports(period, limit)`：按 `week_start` 倒序取历史周报。
- `get_latest_weekly(period)`：取最新一期。
- `get_surfaced_since(cutoff, min_score)`：窗口内已上墙日报条目（JOIN items + summaries，`surfaced_at >= cutoff AND score >= min_score`）。

## 13. 踩坑记录（Phase 3）

1. **LLM 输出 JSON 被截断**：初版 `max_tokens=2500`，输入 50 条日报 + 每领域 1-3 条亮点输出超长，DeepSeek 在 highlights 中途截断 → `Unterminated string` 解析失败。修复三管齐下：
   - 输入侧 `_one_line()` 把每条目的长摘要压成 ≤80 字一句话，降低输入体积；
   - 输出侧 `max_tokens` 提到 4000；
   - 提示词限制亮点数量（每领域最多 2 条、全篇最多 12 条）。
2. **标题日期幻觉**：LLM 在 title 里自推算日期（写成 09-08 ~ 09-19），与实际窗口（09-12 ~ 09-19）不符。修复：把 `week_start/week_end` 以 `{range}` 注入提示词，明确要求「时间范围固定使用给出的范围、不要自己推算」。
3. **PowerShell 误报 exit 1**：LiteLLM 拉取远程模型价格表超时写 stderr，PowerShell 把它当作 NativeCommandError 报 exit 1；实际 Python 流程已成功（日志 `weekly done` + 输出文件 + 正常 flush）。判定标准以日志与产物为准。
