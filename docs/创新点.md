# AI4S-Daily 创新点清单

> 本文档集中记录项目的全部创新点 / 亮点 / 巧思，与《考核复习.md》分开，方便单独背诵与答辩引用。
> 每个创新点按「是什么 → 怎么做的 → 为什么算亮点 → 可追问点」四段展开。

---

## ① 两阶段评分 + 总结流水线（成本控制核心）

- **是什么**：把「评分」和「总结」拆成两个独立阶段，先评分后总结。
- **怎么做的**：
  - 阶段一 `_score_one()`：对 7 天内所有未打分条目**全量**打分（0-10 分 + tags + field）。
  - 阶段二 `_summarize_one()`：只对「分数过 `score_threshold` 且排在 `top_n`」的条目写摘要。
  - scorer 用便宜模型（`claude-haiku`），summarizer 用强模型（`claude-sonnet`）。
- **为什么算亮点**：打分跑全量（70+ 次），总结只跑 top_n（10 次）。把贵模型调用压到最小，成本差 5-10 倍，是整套系统每天能低成本自动跑的关键。
- **可追问点**：为什么不全用贵模型？——成本 + 响应速度；评分只需要相对排序，不需要高质量长文本。

## ② `surfaced_at` 单字段实现「今日 / 归档」分栏

- **是什么**：用一个时间戳字段区分「今日新增」和「归档」两栏，而不是建两张表或两个标记位。
- **怎么做的**：
  - summaries 表加 `surfaced_at`（首次上墙时间，默认 NULL）。
  - 今日 = `surfaced_at IS NULL OR surfaced_at >= 今天零点`。
  - 归档 = `surfaced_at IS NOT NULL AND surfaced_at < 今天零点`。
  - `render` 结束时 `mark_surfaced()` 把本次展示的条目标上当前时间。
- **为什么算亮点**：零额外表结构；同一天重复 render 仍在「今日」，跨天自动掉进「归档」，语义完全由「日期比较」推导，不用维护状态机。
- **可追问点**：为什么 `>= 今天零点` 而不是 `>= 上次 render 时间`？——按自然日分栏更符合「日报」直觉；用零点做锚点避免同一天多次 render 造成误归档。

## ③ 补总结 backlog + 陈旧清理（修设计漏洞）

- **是什么**：修一个真实 bug——「打了分、过了阈值、却被 top_n 挤掉」的条目，永远没机会再被总结上墙。
- **怎么做的**：
  - `purge_stale_unsummarized()`：删掉「只打了分、没写摘要、超过 7 天」的陈旧分数行，避免旧候选久留后突然上墙。
  - 打分循环只统计 `passed_threshold`（本轮过阈值的条数），**不维护内存候选列表**。
  - 打分之后一条 SQL `get_scored_unsummarized()` 拿走**全部候选**：本轮的 + 上一轮遗留的（都有分、`innovation IS NULL`、仍在 7 天窗口），按分倒序取 `top_n`。
  - `backlog = 候选总数 - passed_threshold`，即上一轮遗留的补总结数。
- **为什么算亮点**：这是从「库里堆了 47 条死数据」的真实问题反推出来的修复；候选只来自 DB 单一数据源，每个 url 一行**天然去重**，无需区分新旧、无需担心重复占满 top_n。
- **可追问点**：为什么 7 天？——和 `get_unscored_items(within_days=7)` 窗口对齐，超过 7 天的内容时效性差，不值得再补。

## ④ `field` 子领域分类 + 纯客户端筛选

- **是什么**：打分时让 LLM 顺手把文章归入一个 AI4S 子领域，前端用 8 个 chips 做筛选。
- **怎么做的**：
  - `score.txt` 提示词要求返回 `field`；`_score_one()` 校验 `field` 必须在 `cfg.subfields` 的 key 里，越界回退 `""`。
  - 模板渲染 chips + 每张卡片的 `data-field` 属性。
  - 内联 JS `filterField(field)` 遍历卡片，`data-field` 不匹配的 `display:none`，不重新请求、不碰数据库。
  - 计数徽章跟随当前 tab：全局 `currentBand` + `refreshFieldCounts()` 动态统计。
- **为什么算亮点**：筛选零后端开销，纯静态站点也能做「分类浏览」。
- **可追问点**：三个踩坑——① 切换领域条数不变（数字是服务端写死的，改 JS 动态统计）；② 归档计数不更新（`<section>` 缺 `id="archive"`）；③ 今日+归档数量混一起（引入 `currentBand`）。

## ⑤ 纯静态零后端前端

- **是什么**：收藏、筛选、tab 切换全部在前端完成，不引入任何服务器。
- **怎么做的**：
  - 收藏：点 ☆ → `localStorage.setItem('ai-daily:star:'+url, '1')`；加载时读回所有 star 键，`cloneNode` 复制卡片到收藏区。
  - tab 切换 / 筛选：内联 JS，零请求。
- **为什么算亮点**：任何静态托管（GitHub Pages 等）都能跑，零运维、可 fork 自托管。
- **可追问点**：代价是什么？——收藏只存本浏览器，不能跨设备共享；要跨设备必须上服务器 + 登录 + 数据库，与「零后端」定位冲突，故主动放弃。

---

## ⑥ URL 主键去重 + 幂等写入

- **是什么**：用 URL 作为内容的唯一标识，从存储层保证不重复。
- **怎么做的**：
  - `items.url` 做主键，重复抓取用 `INSERT OR IGNORE`（首次保留）。
  - summaries 用 `ON CONFLICT(url) DO UPDATE`（覆盖更新，重打分不新增行）。
  - 外键约束保证 summaries 的 url 必须存在于 items。
- **为什么算亮点**：URL 是内容的天然身份证；幂等意味着定时任务每天跑多少次都不会产生脏数据。
- **可追问点**：为什么 items 用 OR IGNORE、summaries 用 DO UPDATE？——items 要保留「第一次抓到的原始内容」，summaries 要保留「最新的评分/总结结果」。

## ⑦ 失败隔离（健壮性）

- **是什么**：局部失败不拖垮全局。
- **怎么做的**：
  - 抓取：`fetchers/__init__.py` 按源隔离，单个源（如 arXiv 429）失败不影响其它源。
  - 总结：单条打分/总结各自 try/except，失败计数后继续。
- **为什么算亮点**：定时任务无人值守，任何一条脏数据、一次网络抖动都不该让整批失败。
- **可追问点**：metrics 里的 `score_errors` / `summary_errors` 就是失败隔离的可观测证据。

---

## ⑧ arXiv 限速（防 429）

- **是什么**：控制对 arXiv API 的请求节奏，避免被限流/封 IP。
- **怎么做的**：抓取器加 `_throttle()`，两次请求之间控制间隔。
- **为什么算亮点**：arXiv 429 有两种——瞬时限流 + IP 冷却；限速从源头降低触发概率，是抓取器稳健性的必要保障。
- **可追问点**：实测还遇到 VPN socks4 代理不被 httpx 支持的问题（`Unknown scheme socks4://`），换成 TUN/TAP 模式解决——说明网络链路里「代理协议」也是要排查的一环。

---

## ⑨ 数据库迁移（向前兼容）

- **是什么**：老库升级不用删库重建。
- **怎么做的**：`init()` 里检测旧库缺列，自动 `ALTER TABLE` 补列（`_migrate_add_surfaced_at`、`_migrate_add_field`）。
- **为什么算亮点**：数据是每天攒下来的资产，向前兼容意味着升级代码不丢数据。
- **可追问点**：迁移是幂等的吗？——补列前先 `PRAGMA table_info` 判断列是否存在，重复 init 不报错。

---

## ⑩ 可观测性

- **是什么**：全流程日志 + 成本统计，跑完一眼看清发生了什么。
- **怎么做的**：
  - `fetch done: fetched=... stored=...`、`summarize done: scored=... passed=... backlog=... purged=... summarized=... cost=$...`。
  - 每条 summary 记录 `scorer_cost_usd` / `summarizer_cost_usd`，可累积统计。
- **为什么算亮点**：LLM 应用花钱是隐形成本，打点成本让「花了多少钱」变成可度量的数字。
- **可追问点**：`backlog` / `purged` 就是为方案 B 新加的可观测指标。

## ⑪ 每日 top_n 封顶（`summarized_at`）

- **是什么**：同一天不管跑多少次 `summarize`，当天新写的摘要总数最多 `top_n` 条（n 在 `preferences.yaml` 里可改）。
- **怎么做的**：
  - summaries 加 `summarized_at` 列（`save_summary` 写入当前时间，旧库迁移回填为过去）。
  - `run_summarize` 里先数 `already_today = count_summarized_since(今天零点)`，再 `budget = max(0, top_n - already_today)`，只总结前 `budget` 条。
- **为什么算亮点**：从根上堵住了「一天跑两轮 summarize → 今日新增翻倍」的口子；额度是数据驱动的（看 `summarized_at`），不是靠内存状态或锁。
- **可追问点**：为什么用「写摘要时间」而不是「打分时间」做额度？——`created_at` 是打分时间，backlog 里打分了很久才总结的条目会漏计；`summarized_at` 才真正代表「今天产出了多少摘要」。

---

## ⑫ 北京时间显示（UTC+8）

- **是什么**：页头时间戳按北京时间（UTC+8）显示，每次 render 更新为「最近更新于」。
- **怎么做的**：`_BEIJING_TZ = timezone(timedelta(hours=8))` 固定偏移（中国无夏令时）；`generated_at = datetime.now(_BEIJING_TZ)` 每次 render 现算。
- **为什么算亮点**：国内用户看 UTC 要心算 +8；用固定 +8 偏移零依赖（无需 zoneinfo/pytz）。
- **可追问点**：为什么用固定 +8 而不是 `ZoneInfo("Asia/Shanghai")`？——中国无夏令时，固定偏移更简单、无时区库依赖。

## 附：一句话版本（背这个）

> 一个**零后端**的 AI4S 日报流水线：便宜模型全量打分 → 贵模型只总结 top_n（`summarized_at` 每日封顶）→ `surfaced_at` 单字段分今日/归档 → `field` 子领域纯前端筛选 → 北京时间渲染 → URL 主键去重 + 失败隔离 + 迁移 + 限速 + 全链路成本打点；并用「补总结 backlog + 陈旧清理」修掉了打分未总结条目不上墙的漏洞。
